## Decisions / Conclusions

- Low/zero ticket volume in a given week is considered normal; ticket volume tends to arrive in waves, sometimes triggered by the team's own transitions (e.g. version upgrades). During quiet weeks, the team can do proactive debugging — checking for issues at sites and opening tickets themselves rather than waiting for sites to report problems (e.g. sites running an old HTCondor version, or pilot overloading).
- The Condor-C entries site-token migration (replacing grid-proxy authentication with site tokens, per entry, in the factory configuration) was confirmed as important, to be done at some point soon — described as the next item on Luis's to-do list after finishing the pilot-monitoring rollout — but not urgent enough to require doing it that same day.
- Grid-universe (Condor-G) submission is technically usable without glideinWMS — the factory node could act as a plain schedd submitting Condor-G jobs directly to a site's CE, with no collector/negotiator needed. However, doing so would mean losing glideinWMS's resource-quota functionality (e.g. splitting resources between analysis/production/Tier0) and would require handling credential management directly; Marco's assessment was that replicating this manually would likely end up reimplementing glideinWMS's existing, already-encapsulated components under different names.
- The GAHP (Grid ASCII Helper Protocol) process is a CE-abstraction layer used by the Condor-G grid manager: the grid manager and GAHP communicate over a local socket/file descriptor using a simple text-based (HTTP-like) protocol; the GAHP is the component that actually opens the TCP connection to the compute element (using the ARC REST interface for ARC CEs, or an internal protocol for Condor-C) and holds the site credentials.
- Submit-file/JDL attributes prefixed with `+` are inserted verbatim into the job ClassAd; attributes without `+` are Condor macros that Condor validates and translates into ClassAd attributes (following a general — not universal — convention of removing underscores and capitalizing words, e.g. `request_cpus` → `RequestCpus`). An unrecognized non-`+` attribute is silently ignored rather than raising an error.
- CE-specific submit attributes (e.g. `Xcount` for Condor-C vs. `RequestCPU`-style parameters for ARC) differ in both name and semantics (e.g. per-core vs. absolute memory accounting) between CE types; this cross-CE inconsistency was called out by both Marco and Luis as error-prone and something they consider largely a self-inflicted (Submission-Infrastructure/glideinWMS-side) complexity rather than an inherent grid-protocol constraint. Neither could explain why `Xcount` continues to be used instead of Condor's own `RequestCpus`/`+RequestCpus`; Marco suggested this may be historical and that Jeff might know the reason.
- A pilot going to "held" status indicates an error between the factory's grid manager and the CE, or between the CE and the site's local batch system; a common case is a pilot silently disappearing from the CE's view (e.g. because the site admin manually removed it, often after it exceeded a memory limit and was killed by the batch system, with some CEs also removing the pilot record in that case), which Condor-G reports back as held/error. For infrequent, one-off occurrences of this kind the team's practice is to simply retry/ignore it (pilots are cheap to resubmit); persistent or frequent occurrences warrant opening a ticket with the site admin to investigate.
- HEPCloud (Fermilab) reuses the same glideinWMS factory code as CMS's Submission Infrastructure, but is a separate project (with separate funding) built around cloud/commercial resources (AWS, Azure, EC2). Its front-end-equivalent component, the "decision engine," differs from glideinWMS's front end mainly in that it accounts for the monetary cost of provisioning (since cloud resources must be paid for, unlike pledged/free grid resources) when making provisioning decisions. Merging the decision engine and the glideinWMS front end into a single project has been discussed previously but has not happened, since prior attempts at adopting the decision engine were considered heavier/less pleasant to operate (more moving parts, its own logging databases) than the current front end.
- The Condor-C-to-site-token migration and CMS's broader token migration are distinct efforts (consistent with a point clarified in a previous week's meeting): this is a factory-to-CE authentication detail.

### Condor-G / grid-universe architecture refresher
As a refresher, Marco reviewed the three core HTCondor pieces (access point/submit node, execution point/execution node, and the central manager, which negotiates matches between the scheduler's jobs and the machines it knows about) and how the `startd` initiates a reverse TCP connection to the `schedd` via the Collector/CCB (central connection broker) — allowing worker nodes to remain behind a firewall/NAT, since the CCB tells the `startd` when and where to connect rather than the connection being inbound to the worker node.

Condor-G refactors this so the submit host acts as a "grid client": in Submission Infrastructure's case, the submit host is the factory, and each factory runs multiple `schedd`s (for scalability reasons that Marco could not explain). A typical grid site has a compute element (CE) fronting a queue that the CE submits into the site's local batch system (HTCondor, LSF, PBS, SGE — Slurm was noted as conspicuously absent from the training slide, likely because it was not yet popular when the slide was made). ARC (Nordugrid) is a comparable, newer type of CE.

### Condor-G daemons and the GAHP
When using Condor-G, the `schedd` does not wait for a match from the negotiator but sends the job directly to the CE. The relevant daemons are the grid manager (one process per user per CE type — historically one per experiment when the OSG factory served multiple VOs, but now only one CMS pilot user) and the GAHP (Grid ASCII Helper Protocol), a separate process the grid manager communicates with over a local socket/file descriptor using a simple text-based protocol (analogous to HTTP). The GAHP is the component that actually abstracts different CE types behind a uniform interface and opens the TCP connection to the CE (using the ARC REST interface for ARC, or an internal protocol for Condor-C), holding the credentials needed to do so. Live inspection on a factory node (`ps`, and files under `/tmp` matching `gahp`) showed the grid manager and its child GAHP process, and the request/response strings passed between them.

### Vanilla vs. grid universe
The vanilla universe (per-job `condor_shadow` on the schedd talking to a `condor_starter`, not `startd`, on the worker node — a `starter` can serve multiple jobs for a single `startd`) was contrasted with the grid universe, where the grid manager plays a role similar to the shadow: managing the job and the remote resource it is connected to. Both universes are handled entirely within HTCondor — operators do not need to choose or install separate "grid" vs. "vanilla" HTCondor builds.

### Submit-file attributes and CE-specific translation
Using a live example (a factory entry XML/submit template for a Condor-C site), Marco and Luis walked through submit-file fields such as `universe`, `grid_resource` (containing gatekeeper/hostname parameters), and CE-specific submit attributes. Attributes prefixed with `+` go verbatim into the job's ClassAd (JDL); attributes without `+` are Condor macros that `condor_submit` validates and translates into ClassAd attributes, generally by removing underscores and capitalizing words (e.g. `request_cpus` → `RequestCpus`), though this is only a rule of thumb, not a strict rule. An attribute without `+` that Condor doesn't recognize as a macro is simply ignored (not an error). Comparing Condor-C (`Xcount`, prefixed with `+`, for CPU count) and ARC (a differently-named, differently-behaving parameter for the same purpose — e.g. per-core vs. absolute memory) submit attributes, both agreed this makes site/entry configuration error-prone (Luis recalled past confusion when first learning to add entries), and Marco suggested this specific complexity (e.g. using `Xcount` instead of `RequestCpus`) is likely historical/self-inflicted on the Submission-Infrastructure/glideinWMS side rather than a fundamental Condor or grid-protocol constraint; he speculated Jeff might remember the original reasoning.

### Held pilots and job-disappearance debugging
A "held" pilot indicates an error occurred between the factory's grid manager and the CE, or between the CE and the site's local batch system, without the job ever reaching the site's actual batch system in some cases. The job's `HoldReason` ClassAd can be misleading. One specific failure mode discussed: the CE can lose track of a job it previously accepted (e.g. because the batch system killed it for exceeding memory, and some sites' CE configurations also remove the corresponding CE-side record in that case, or because a site admin manually ran a `condor_rm`-equivalent on the CE); when Condor-G later polls the CE for status, it gets a "job not found" response and marks the pilot held (potentially even if the job might still have been running). To resolve this, the team opens a ticket with the site admin to determine the cause, but for occasional/one-off occurrences the general practice is simply to retry and let a fresh pilot replace it, since pilots are inexpensive to resubmit.

### HEPCloud vs. glideinWMS front end
Prompted by the "grid types" section of the Condor documentation (which also covers cloud grid-types for talking to cloud provider APIs), Marco described HEPCloud as a separate Fermilab-based project (distinct funding/accounting from CMS's glideinWMS factory) that reuses essentially the same factory component but pairs it with a different front-end-equivalent, the "decision engine." The decision engine's key difference from the glideinWMS front end is that it factors in resource cost, since cloud resources (AWS, Azure, EC2) must be paid for, unlike pledged/free grid resources. Merging the decision engine and glideinWMS front end into one project has been discussed previously but has not happened; Marco's own past attempts to use the decision engine found it heavier to operate (more moving parts, additional logging databases) than glideinWMS's front end.
