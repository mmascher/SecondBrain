# Submission Infrastructure Weekly Meeting

## Summary

Antonio opened with a report on CMS's readiness to use ARM resources, discussed the previous day in the general computing meeting: Marco had tested the full chain end-to-end and found several latent issues that had accumulated since ARM support was last configured and exercised (apparently as long as one to five years ago). These included a default HTCondor architecture-matching requirement blocking ARM pilots unless a submit attribute and a custom requirements expression are set, a typo in the OS-to-container-image mapping for EL8/EL9 (now fixed), a missing EL9 build of a specific Python version needed by WMAgent-submitted CMSSW jobs, and an unresolved issue where KIT pilots are not being triggered. Stephan gave context from the CSA side: full ARM readiness is not expected within days, with a proof-of-concept validation planned once Annette arrives in a few weeks, and a milestone (per Pat's CSA presentation) targeting the first half of the year. Marco proposed pinging computing-operations contacts and workflow-management people to set up an independent end-to-end test workflow once the KIT matching issue is fixed. The group also settled on which packages to list in response to a Level-1 critical-software-packages survey (HTCondor, glideinWMS, and Singularity/Apptainer), briefly reviewed the Monday-meeting discussion on analysis-job overflow from Tier-1s to Tier-2s (no action needed for Submission Infrastructure), and Marco reported from the client/decision-engine meeting on GPU splitting plans and upcoming stakeholder/CHEP scheduling. On infrastructure status, the team discussed unexplained gaps in collector-query monitoring (for both the global and Sun pools) that don't correlate with collector saturation, host machine load, or the CMS@Home Apache/symlink issue that recurred on the volunteer and ITB front ends and was fixed again by pointing Apache directly at `/data`. Luis gave a factory-operations update covering new NVIDIA MIG-based GPU entries (with Apptainer/nested-container issues still being debugged), GPU entry sizing (16 CPUs plus GPU), and the still-broken overload-enabled monitoring, which Luis suspects is due to filtering being applied after rather than before aggregation. He also reported progress on pilot-efficiency-for-overloading monitoring, expecting to start sending test payloads to AMQ within a few days. Antonio closed noting no BSC/dynamic-resources update this week beyond mentioning Carlos's in-progress talk on resource monitoring/tagging.

## Decisions / Conclusions

- For submission infrastructure's response to the Level-1 critical software packages survey, the group agreed to list HTCondor, glideinWMS, and Singularity/Apptainer as the critical packages, per Stephan's original suggestion.
- The OS→container-image key mapping typo affecting EL8/EL9 (EL7 was already correct) has been identified and fixed by Marco.
- The EL8 build of the specific Python version needed by WMAgent-submitted CMSSW jobs (from the dedicated CVMFS area, separate from the standard CMSSW area) is present and should be working; only the EL9 build is missing. Shazad is understood to be responsible for producing EL9 builds of this Python distribution, though he has not yet been asked to do so.
- The KIT pilot-triggering issue is not yet resolved; Marco suspects something broke in a matching expression in the frontend, but has not found the root cause. The CERN frontend is confirmed working, which is why CERN could be tested.
- On analysis-job overflow (from the Monday operations meeting): the conclusion for now is not to further increase the percentage of analysis slots dedicated at Tier-1s; instead CMS will rely on overflow from Tier-1s to neighboring/regional Tier-2s via CRAB's desired-site-list expansion, which is ongoing work (Stefano). Antonio noted this has no required action for Submission Infrastructure.
- Regarding the recurring CMS@Home Apache issue: the root cause is that Apache (as a security measure) does not follow the `/var/lib` → `/data` symlink used in the front-end setup, even though the same setup and Apache version reportedly still works on the global front end; the fix (pointing the Apache config directly at `/data`) was applied to both the volunteer and ITB front ends, resolving the issue for now. Since the affected config file is not managed by Puppet, the fix should persist unless the front end is reinstalled from source in the future. The reason the symlink stopped working is unresolved (config checksums, Apache version, and installation date were all checked and found consistent between working and broken front ends).
- The overload-enabled monitoring bug is still not fixed: querying the collector shows an increasing (not decreasing) number of CERN-pool slots with `glide-in overload-enabled` reported as undefined, even for entries that shouldn't have this problem, so it is not simply a matter of waiting for old pilots to recycle. Antonio's working theory is that the aggregation query applies its filter after the query result is returned rather than before aggregation, causing invalid values to leak in.
- Collector monitoring gaps (missing data points in the global-pool duty-cycle plot) are confirmed not attributable to collector saturation (duty cycle is low) or to visible load on the monitoring host machine; the cause remains unidentified.

## Discussion

### ARM resource readiness and bugs found by Marco
Following the previous day's general computing meeting discussion on CMS's readiness to use ARM resources, Marco tested the full chain and found several issues, described by Antonio as consequences of configuration that was set up once, worked, and then was never exercised intensively again (Marco recalled a similar test having been done one to five years earlier, with Nikos involved at the time):

1. By default, HTCondor sets a requirement that pilots match the submitting machine's architecture. In the past, CEs apparently did not enforce this requirement themselves and instead relied on the frontend/factory correctly steering pilots to the right resources. To support ARM, glideinWMS needs to set a submit attribute for the target architecture and a corresponding requirements expression on the pilot, since a factory/frontend may serve multiple CEs that aren't each dedicated to a single architecture/subcluster.
2. The OS-to-container-image mapping (a dictionary keyed by operating system) had a typo affecting the EL8 and EL9 keys — the EL7 mapping was correct, but EL8/EL9 had incorrect keys, discovered because Marco had previously tested EL7 and only recently switched to testing EL9. This has been fixed in the glideinWMS configuration.
3. WMAgent jobs submitted to run CMSSW look for a specific Python version compiled and located in a dedicated CVMFS area (distinct from the standard CMSSW area). Marco learned from Alan that Shazad is responsible for building the EL9 distribution of this Python; it doesn't yet exist for EL9, but nobody has asked Shazad to build it yet. The EL8 version (the current production version) is present and should be working.
4. At KIT, despite reported job pressure, pilots are not being triggered. Marco has been investigating without yet finding the cause, suspecting something in the frontend's matching expressions; CERN's frontend was confirmed to be working (which is how the other tests above were validated). Marco said he would look into the KIT issue and report back.

Only three sites currently have ARM resources: CERN, and two others referred to in the transcript as "CERNA"/"Knaff" (unclear/possibly mistranscribed) and KIT, together providing on the order of a few thousand cores.

### Infrastructure status: collector monitoring gaps
The pools are generally healthy, but there continue to be gaps ("hiccups") in monitoring, appearing as missing data points, particularly for the global pool's collector-query-based plots (also observed, per Stephan's comparison of plots, on both the primary and secondary/backup collectors). Antonio noted this pattern normally indicates the collector is saturated and failing to respond to queries in time, but ruled this out here since the collector's duty cycle is far from saturated. His working hypothesis is that when the global pool (with more resources/slots) is queried, the response might occasionally take longer than an implicit query timeout, though this is hard to reproduce and doesn't show up in Antonio's own alternative, independently-based monitoring.

Florian had not identified the cause: the messaging-queue rate for messages sent to the monitoring topic dropped during the gap windows, suggesting the issue is upstream of monitoring ingestion (messages simply weren't sent), but the reason is unclear. The relevant cron job's Python script currently redirects all output to `/dev/null`, so there are no logs to inspect; Marco suggested redirecting this output to a file going forward so that, if there's a network issue or something else, it can be diagnosed. Stephan suggested checking the physical host's networking plot (e.g., via Ganglia/Grafana for the hypervisor) in case the VM's host network interface is being oversubscribed by other VMs on the same physical machine, which wouldn't necessarily show up in the VM-level plots Florian had already checked. Florian said he could identify the hypervisor and corresponding Grafana dashboard without needing to involve CERN, and reported checking the host machine's own monitoring live during the meeting, but did not see spiky behavior that would explain the gaps (the host's monitoring history only goes back about three days; the most recent gap was around 4 a.m. that day, with no correlating spike visible in CPU usage, which looked mostly idle). Luis separately noted that P5 is decommissioning machines for high-level-trigger use (moving some to dedicated offline duty, related to the shutdown timeline: 2017 notes are being shipped out around now, with 2018 notes shutting down in early May), which Antonio thought might partly explain an increase in resources he'd separately noticed at T2/P5, though this remains a tentative correlation with the monitoring gaps rather than a confirmed cause.

### CMS@Home Apache/symlink issue
CMS@Home had issues again but they were fixed; Antonio remarked this consumes more attention than the resources it provides are worth. Florian explained the underlying issue: the CMS@Home setup mounts an external disk at `/data`, but the glideinWMS-shipped web server serves from the hard-coded path `/var/lib`, so historically a symlink from `/var/lib` to `/data` was used and worked — until it stopped working (first on the volunteer front end, then, as Luis found while troubleshooting a separate GPU-entry issue, on the ITB front end as well). The fix applied in both cases was to change the Apache configuration to point directly at `/data` instead of relying on the symlink; Florian attributed the original failure to an Apache security feature that prevents following symlinks in some circumstances (to avoid inadvertently exposing the filesystem), though the root cause of why it suddenly stopped working is unresolved: the affected Apache config file was last changed a year ago, the same Apache version (from December 2025) is running on the (still-working) global front end and on ITB, and config file checksums matched across the front ends investigated. Because this config file is not managed by Puppet, the applied fix should persist unless the front end is reinstalled from source for a future glideinWMS version. Marco proposed periodically restarting the global-pool front end intentionally, so the team can detect this kind of issue proactively rather than being caught by it unexpectedly.

### Factory operations (Luis)
Several factory entries remain under test; one Tier-1-related entry has been revisited via an old ticket dating to the start of the year for five new GPU entries, all configured with NVIDIA MIG, which Luis expects to be able to test soon. While troubleshooting this entry, Luis ran into the CMS@Home frontend issue described above, and separately is going back and forth on Apptainer/Singularity issues at this new GPU site, where pilots run nested inside Docker containers. Stephan suggested Luis could debug this using the same Apptainer test/probe that the factory's glidein startup script uses for Singularity/Apptainer discovery, running it manually inside the container, which might be easier to isolate than debugging via the full glidein startup script. Separately, Stephan advised against setting Singularity-specific environment variables at the level of an individual factory entry, since future clients (referred to as "Sam" in the transcript) would not see them — any override needed for Singularity binary location, etc., should instead be set by the site itself; Luis acknowledged and retracted a related suggestion he had made in the ticket, noting this would also need to be replicated across all factory entries for a given site if done that way.

On GPU entry sizing: Luis confirmed that for the new GPU entries the default CPU request (16 CPUs) and memory are used, plus a GPU request; HTCondor's GPU discovery tool then discovers available GPUs on the worker node. On these MIG-based worker nodes, all slots are currently being made available to jobs, so the pilot should discover and advertise all of them, though this has not yet been confirmed since testing hasn't reached that step. One entry is otherwise ready to move to production, pending sign-off from the site admin.

On overloading parameters: a known monitoring plot for pilot overloading is still broken. The fix (addressing inconsistent overloading-related values) was applied to the factories the previous Friday, and Luis had been monitoring through the week expecting pilots to recycle with corrected values, but the plot remains broken. Querying the collector directly, Luis found the CERN pool still has slots reporting `glide-in overload-enabled` as undefined, and this count has been increasing rather than decreasing, which rules out simple pilot-recycling lag as the sole explanation; the affected entries are all whole-node entries, though Luis is unsure if that's related. Antonio, looking at a specific site that should not exhibit this problem at all, suspects the issue is in how the monitoring aggregation query is built: the query likely applies its filter to already-aggregated results rather than filtering before aggregation, so invalid values from unrelated fields/records leak into the result. Luis had already manually edited the dashboard query to filter for valid values but is still unsure why the problem persists, and will ask Carlos about it.

Luis also reported progress on pilot-efficiency-monitoring for overloading: work this week (alongside "Frontier training") got to the point of being able to generate the payloads; he plans to test sending them to AMQ within the next few days and expects to start pushing data to a test index soon after.
