# Overload-Enabled Fix Planning and HTCondor Condor-Overview Training

## Summary

Marco Mascheroni and Luis Simas worked out the concrete factory-side implementation plan for the `glide-in overload-enabled` monitoring/type-casting fix that had been agreed in principle at the previous day's weekly meeting, then spent the rest of the session on the second part of Luis's HTCondor training series ("condor overview"), covering ClassAds, the matchmaking algorithm, the daemon architecture, the claiming/activation protocol, and partitionable vs. dynamic/static slots, with live exploration of the production collector throughout.

## Decisions / Conclusions

- The front end's `glide-in overload-enabled` value will be changed to string `false` for consistency, and the group agreed it can likely be removed from the front end altogether afterward, since factory-level configuration will become the sole source of truth for this setting.
- Going forward, overloading will be controlled entirely in the factory, per site rather than per entry: whenever any entry at a site has the 66% overload value enabled, all other non-GPU entries at that same site must also have it enabled, to avoid the inconsistent state found today (at least one site had overloading enabled on some entries but not others because an operator, Viva, forgot to enable it everywhere when converting from the old true/false scheme to the 66% scheme).
- For all entries that should **not** use overloading (including all GPU entries), the factory must explicitly set `glide-in overload-enabled` as `constant true` with value string `false`, to override whatever the front end provides. Marco noted the front end's override does not appear to work as expected for this specific attribute — setting it `constant false` in the front end did not appear to let the front-end value win, which he suspects may be a glideinWMS bug; he was not fully able to confirm this during the meeting and referenced a ticket (not identified further) where the original collapsing behavior was implemented.
- Root cause of the monitoring mismatch: when the attribute is left as an expression, the factory does not use the front-end value at the matching/collapsing stage, but later in execution the front-end string value (e.g. `"66%"`) gets cast to a boolean, and any non-empty string casts to `true` — so entries without an explicit override end up reporting `true` regardless of the intended 66%/false split. Using type `string` consistently (not boolean or expression) avoids this; Marco recalled that using type `boolean` had not worked in earlier testing, though he did not remember the exact reason.
- GPU entries are identified by the `GLIDEIN_Supported_VOs`-type attribute containing `CMS-GPU` (the attribute actually read by the front end); the `_GPU` suffix commonly used in entry names is only a naming convention, not the authoritative signal.
- This change only applies to CMS-owned factory XML configuration files (not shared files used by other VOs), since both `glide-in overload-enabled` and CMS GPU support are CMS-specific; Luis will check other CMS-entry files beyond the one reviewed live and include any needed changes in the same pull request.
- The team's general practice is not to make infrastructure changes on Fridays, with exceptions for low-risk changes (e.g. adjusting an entry's wall time); installing new software versions is considered too risky for a Friday change.
- The overload-enabled factory change was judged a bigger change to be done on Monday rather than same-day; Luis will open a GitHub pull request for Marco to review.
- The current overload value used everywhere overloading is enabled is 66%; a gradual rollout to higher values (e.g. up to 100% for Tier-1s) was discussed as a possible future direction, not decided. It was reaffirmed that overloading is deliberately not enabled at all sites — some sites are excluded for reliability/efficiency reasons or local site policy — and that any move to enable it more broadly requires management sign-off.

## Discussion

### Overload-enabled fix implementation planning
Continuing from the previous day's weekly meeting, Marco walked Luis through the factory/front-end configuration live (using an example GPU entry and a Wisconsin entry) to explain how the `glide-in overload-enabled` attribute currently behaves. He clarified the general front-end/factory override model: an unset or expression-type value in the front end is normally overridden by the factory value, unless the front end explicitly sets the value as `constant` (true or false), in which case the front end wins. However, for this specific attribute the collapsing logic behaved differently than expected, which Marco flagged as possibly a bug and wanted to verify further.

The two of them worked out that the practical fix combines a front-end type change (string instead of expression, for consistency) with a factory-level policy: enable overloading per site (not per individual entry) for all non-GPU entries, and explicitly force-disable it (constant true, string `false`) everywhere else, so the front end's value is never relied upon at execution time. Luis noted this effectively makes the front-end value irrelevant once the factory-side fix is in place, which Marco agreed with, adding that removing the front-end knob afterward avoids needing to think about it going forward.

### Factory change-management norms
Luis asked about the team's policy on making changes on Fridays; Marco confirmed the general rule against Friday changes (particularly installing new software versions), while noting simple entry-level tweaks are treated as low-risk exceptions. Luis proceeded with a small, low-risk change (reducing the wall time on an entry, requested by Thomas) during the meeting, and separately after the meeting, consistent with this norm; the larger overload-enabled change was deliberately deferred to Monday and routed through a pull request and code review rather than being pushed directly.

### HTCondor condor-overview training
Marco continued the HTCondor training series with a second talk, using the "old" access-point/execute-point-vs-schedd/startd terminology to match the existing slides, and again fed the session transcript and slides into ChatGPT afterward (as done for the previous day's session) to help produce CMS documentation material. He noted the Zoom transcript currently has to be manually saved via "Save Transcript" before leaving a meeting, since automatic cloud-saving has not yet been configured.

Topics covered:

- **Usage modes of [[HTCondor]]**: managing a local (vanilla) cluster, connecting clusters via flocking, building resource overlays with [[glideinWMS]] (used for the global pool), or accessing external compute elements via `condor_G`.
- **Jobs and machines**: jobs (unit of work, like a Unix process, potentially part of a larger workflow split into independent chunks — the "throughput" in high-throughput computing, contrasted with HPC's tightly coupled parallel processes) live on the scheduler/access point; machines (execute points) are tracked by the collector. Jobs are queried with `condor_q`, machines with `condor_status` — distinct entities and distinct query tools, though conceptually analogous.
- **ClassAds**: a key-value description language (string, boolean, integer, float, or expression-valued attributes) used by both jobs and machines to express requirements and preferences/rank, tracing its name to a matchmaking analogy with newspaper classified ads. `my.` and `target.` prefixes disambiguate "self" vs. "the other side" in an expression (reversed meaning depending on whether the expression is evaluated in a job's or a machine's context); if no qualifier is given, HTCondor looks first in the local ClassAd, then the candidate's ClassAd. Type-checking operators (e.g. for handling `undefined`) and the three-argument `ifThenElse` function were shown as common patterns, e.g. providing a default when `RequestMemory` is undefined.
- **Rank and machine ordering**: rank expressions (e.g. `-Cpus`, generally used to prefer smaller/less-fragmented machines and avoid fragmentation) order matching machines for a job; Marco was unsure whether the associated `MaxCores` handling (thought to relate to disused "resizable jobs") is still relevant, and was not certain rank is actually in active use today.
- **Matchmaking**: for each job, the negotiator sorts candidate machines by rank and evaluates requirements on both sides; the first mutually-satisfying match is used. The negotiation cycle target is under 5 minutes for the whole pool, because a glidein that fails to get a match within about 10 minutes shuts itself down — a sub-5-minute cycle guarantees at least two match opportunities. HTCondor uses machine/job clustering internally to make this tractable at scale.
- **Central manager and collector**: the collector holds machine ClassAds and also collects information about other components (e.g. schedulers) reachable via `condor_status -sched -l`; `condor_status -r` prints raw (unevaluated) ClassAd values instead of the default evaluated/cast form.
- **Daemon architecture**: `condor_master` starts and supervises the other daemons (restarting them and notifying the administrator on unexpected exit, and also restarting a daemon if its binary is updated); `condor_schedd` maintains a persistent job queue (`job_queue.log`) with priority-based rather than strict FIFO ordering; `condor_shadow` (one per running job, on the submit side) handles file transfer and enforces periodic expressions such as `periodic_remove`/`periodic_hold` (e.g. CRAB removing jobs that exceed requested memory); `condor_startd` represents a machine willing to run jobs and enforces the machine owner's policies; `condor_starter` (one per running job, spawned by the startd) manages starting/running the job and reporting exit status; `condor_procd` tracks process birth/death and resource consumption for other daemons; the negotiator performs matchmaking and also handles user priorities/accounting. The `condor_master`/CCB were confirmed to also exist on the schedd side even though not shown on the discussed slide.
- **Claiming and activation protocol**: schedd and startd both advertise ClassAds to the collector; the negotiator matches a job to a machine and informs the schedd. Because glidein startds typically run behind firewalls/NAT and cannot accept inbound connections, activation uses a reverse-connection mechanism: the startd maintains a persistent TCP connection to the CCB (central collector broker) on the central manager, and the CCB instructs the startd to open a TCP connection to the schedd to establish the claim. Once claimed, the schedd activates the claim (picks a queued job matching that machine) and starts a `condor_starter` on the machine side and a corresponding `condor_shadow` on the schedd side; the shadow transfers input/output files and tracks the running job (e.g. which pilot/machine a given user job is running on is information the shadow obtains from the starter). After a job finishes, the schedd does not release the claim — it can reuse the same starter/claim for another matching job without going back to the negotiator, reducing negotiator load. Claim lifetime (~4h) is shorter than the typical target job runtime (~12h), but an expiring claim does not interrupt an already-running job.
- **Schedd scalability**: each running job's shadow process costs roughly 2 MB of memory on the schedd, and the team hit a scalability limit around 50,000 concurrent shadows the day before the meeting. Marco believed (but could not fully explain) that the shadow is implemented as a separate process rather than a thread for isolation reasons, having heard an explanation from an HTCondor developer at a Condor Week that he no longer recalled in detail.
- **Central manager / collector scalability**: the central manager is a single point of coordination (with backups) and cannot be horizontally scaled the way schedds can. In practice there are multiple secondary collectors, each on its own TCP port; each machine is randomly assigned to one secondary collector via TCP, and each secondary collector periodically forwards its state to a single top-level collector locally via UDP (chosen since the transfer is local). The top-level collector is the actual bottleneck; under high update load its UDP receive buffer can fill and updates are lost until it catches up. Scaling options are limited to a faster machine or splitting into multiple top-level collectors (at the cost of a single unified view of the pool). Marco noted the HTCondor developers have their own idea for improving this — having secondary collectors send only diffs rather than full state to the primary collector — which CMS has not yet pushed for since it is not yet at the relevant scalability limit.
- **Multiple negotiators**: the global pool currently runs 3 negotiators (Tier-1, Tier-2, and the rest) each enforcing different resource quotas/policies, all using the single top-level collector; a separate central manager (for the "sample" pool) runs its own single negotiator. Luis raised a concern that partitioning across negotiators/collectors could fragment the pool into smaller, locally-optimized views instead of one global view; Marco clarified this is not a problem in practice because negotiators partition machines but not jobs — every negotiator sees the full job list, so full-pool matchmaking is still effectively performed. Marco informally described the current setup as roughly 4 "sub-pools" split across 2 pools (his own term, not established terminology), reflecting that further splitting is technically possible (with more monitoring/frontend configuration overhead) but not something currently planned.
- **Partitionable vs. static/dynamic slots**: a partitionable slot (e.g. `slot1`) represents a whole machine's available resources and is not itself matched to run a job directly; when a match occurs, a dynamic child slot (e.g. `slot1_7`) is carved out of it with the job's requested CPU/memory subtracted from the parent. The partitionable slot always shows as unclaimed (potentially with zero available CPU/memory once fully allocated), while dynamic slots show as claimed with the requested (not actual-usage) CPU/memory of their job. A static (non-partitionable) slot, such as a dedicated high-I/O slot, is claimed directly as a whole unit with no further partitioning. Both partitionable and dynamic slots report separately to the collector, so a larger number of small jobs increases the collector's update load. Only the partitionable (parent) slot participates directly in matchmaking; dynamic slots are a byproduct of a match rather than independently matched. The front end's total-slot counting limit (previously discussed as 200,000/220,000) counts static, partitionable, and dynamic slots together, which Marco described as historical and slightly counterintuitive, attributing it to glideinWMS predating HTCondor's partitionable-slot feature.
- Live inspection of the production collector during the session also showed overloaded machines advertising a higher `Cpus` count than physically present (e.g. 8 physical cores advertised as 10 due to overloading), consistent with prior discussion of the CPU overloading mechanism.

Luis reflected that the system, while handling a genuinely complex problem, is elegant in its core design (ClassAds, matchmaking) and reused a small set of concepts consistently; he said the matchmaking process and slot model were now much clearer, building on an earlier informal briefing from Antonio.
