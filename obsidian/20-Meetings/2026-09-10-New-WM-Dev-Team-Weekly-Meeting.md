# New WM Dev Team Weekly Meeting

## Summary

The regular structured meeting had been cancelled because Kevin Lannon was on holiday, but Marco Mascheroni and Valentin Kuznetsov used the slot for a technical discussion, joined also by Kevin Lannon (mostly listening), Francesco Brivio, and Camille Mauceri (invited specifically to discuss her proof-of-concept work).

The main topic was reproducibility of the DiracX proof-of-concept deployment on Kubernetes. Valentin Kuznetsov raised concerns that Marco Mascheroni's current approach — manually `git clone`-ing his development code into the `SRC` area inside a running pod and re-running `pip install -e` (an "editable" install, relying on DiracX's mounted-Python-modules / entry-point-registry mechanism) — is not reproducible: the code lands on a PVC, and Valentin's Helm chart setup (via USA-CMS/Usacorn's storage class) deletes and returns PVCs to the pool on `helm uninstall`, so there is no way to reconstruct that state from a clean `helm install`. Valentin argued that patching code inside already-built images/deployed pods leads to "dangerous, non-reproducible behavior," especially as the project moves toward more stable releases, and that the Kubernetes deployment should track stable, tested images rather than becoming an implicit development platform; he also noted the DIRAC team itself appears to have a different, shorter-term perspective of using the Kubernetes/developer-mode setup for rapid development and testing, though he is unsure if that reflects the DIRAC team's long-term intent. Marco Mascheroni agreed with the general direction but noted `pip install -e` (rather than plain `PYTHONPATH` manipulation) is still needed because DiracX discovers tasks (e.g. the proof-of-concept's Condor-submission-monitoring task) via Python's package registry, and a `PYTHONPATH`-only approach had thrown exceptions when he tried it.

The agreed path forward is to make the Helm chart itself perform the `git clone` of the developer's repository (configurable via the values manifest, specifying which Git repository/branch to use) inside the `entrypoint.sh`/config-map logic, after the existing `cs_sync`/initial-repo block, guarded by a conditional that checks whether a Python module is requested/configured locally — rather than requiring any manual step after deployment. Valentin will post the current commands and Helm values he uses (via Mattermost, and his `values` file copied to a public AFS area, since the files may contain sensitive information) and has already flagged which file is responsible for the entry point. Marco Mascheroni will implement the `git clone` addition to the Helm chart and coordinate offline with Valentin on the exact commands, with the intent to eventually backport this change to the upstream DiracX Helm chart, since CMS's chart has diverged from it. Valentin also recommended always doing a full `helm uninstall` + `helm install` cycle (clean state) rather than manual `helm upgrade --set` commands on top of an existing installation, since the latter does not reproduce the installation from scratch; Marco acknowledged he had been using `helm upgrade` as a stopgap while Valentin was on vacation and agreed to switch to the clean-install approach. Marco will not be available at all next week (returning to CMS/Run 3 preparation duties) but will be responsive to quick questions; Marco will take over hands-on work in the meantime.

Separately, Marco Mascheroni reported finding a DIRAC client already distributed via the LHCb CVMFS instance that anyone can use, with setup instructions posted on the team's Mattermost channel; once test18 is confirmed working, any user with a test18 account (after being authorized via a small configuration-file addition) will be able to submit jobs through it using standard CERN SSO authentication. Valentin Kuznetsov noted a remaining gap: DiracX currently uses self-signed certificates, and the team needs Usacorn to provide/locate a proper set of persistent certificates for test18 so the client does not need reconfiguring after every Helm reinstall; Marco agreed to contact "Q" (the relevant Usacorn colleague) about this, pointing her to the Helm chart repository.

Francesco Brivio asked for confirmation that once test18 is set up from Marco's development branch, it would include the code he, Marco, and Camille have implemented; Marco confirmed this, explaining the `developer=true` Helm chart flag signals the installation to fetch not-yet-released code. Marco gave a high-level recap of the current proof of concept: direct job submission writes to the DIRAC job database; a task Marco implemented polls that database, submits matching jobs to HTCondor, and updates their status to "submitted." The missing piece — a task that checks job status on the Condor/worker-node side and updates the database when jobs complete, closing the loop — was discussed as worth doing, and Francesco Brivio volunteered to work on it (after first addressing an unrelated JDL-related fix from that morning).

The largest remaining segment concerned Camille Mauceri's proof-of-concept work on transferring input sandboxes (code/files a job needs, as opposed to CMS "input files" in the data sense) to jobs submitted through the Kubernetes-deployed DiracX server, since — unlike her earlier local-only test where client and server were on the same machine and could share files directly — the Kubernetes deployment requires uploading input files to wherever the server can see them. Marco explained that DiracX's local ("pixel"/`dirac serve local`) setup uses a component called "seaweedfs" (an S3-protocol-compatible object store, a Go library) for this, while the CMS web Kubernetes cluster instead uses MinIO, another S3-compatible implementation, because Valentin was not convinced by seaweedfs's licensing model. This triggered a broader discussion: Valentin argued CMS has made no collaboration-level commitment to use S3 as a general storage layer, and questioned spending effort on licensing/integration work for a feature (seaweedfs) that may not be needed, especially since DiracX's own internal dependencies apparently use more than one S3-library implementation (MinIO and, per Valentin, something else/"CVEED") for unclear reasons — he proposed first understanding why and where DiracX actually needs the S3 layer, and treating this as a question to raise with the DIRAC team, before committing further effort. Marco pointed out CRAB already relies on an S3-compatible object store at CERN for shipping user sandboxes to worker nodes, so if CERN's existing S3-compatible service could simply be swapped in via URL configuration for CMS's DiracX deployment (avoiding new licensing costs), that would be the ideal outcome, though this needs further investigation to confirm it's that simple. Kevin Lannon noted that DIRAC/DiracX's use of a standard S3 protocol should in principle make the backend implementation swappable, and separately raised a broader point from CMS's earlier (pre-DIRAC-adoption) aspiration to unify WMAgent (production) and CRAB (analysis) tooling: one underlying difficulty was that production historically didn't need to think hard about sandboxes (code is centrally tagged and pulled from CVMFS), while analysis sandboxes are per-user and highly variable — Kevin urged the team to treat sandbox handling as a first-class, central concern going forward rather than an edge case, noting DiracX's S3-based sandbox support seems well aligned with this need. The group agreed to continue using whichever S3 implementation is already deployed for now (seaweedfs locally, MinIO on the CMS web cluster) while keeping an eye on the longer-term architecture question, and to revisit formally requiring standard/portable S3 support if this isn't already addressed by the DIRAC team's ADRs (Architectural Design Reviews).

After Valentin and Kevin left, Marco and Camille did a live, exploratory debugging session (with Marco sharing his screen and consulting ChatGPT) trying to get input-sandbox upload working via the `dirac job submit` client and an `InputSandbox` JDL attribute, without reaching a firm conclusion in the meeting. Camille explained she had been experimenting with including her X509 proxy directly in the input sandbox as a way to pass Kubernetes-cluster credentials to a Monte Carlo test job, and flagged this as feeling insecure; Marco agreed proper credential handling needs more discussion, and suggested that, for the proof-of-concept stage, following whatever CRAB does (CRAB uses a CMS-provided tool to move credentials around) or even just adding the proxy as a plain input file would be an acceptable simplification for now. Camille reported separately that she had needed to tar multiple sandbox files together before upload, and mentioned HTTPX being involved in the client's upload path, and said she would continue investigating and report progress via Mattermost. Marco had to leave for another meeting (Submission Infrastructure meeting) at 4pm, one hour after this meeting started, and the session wound down shortly after with no further business.

## Decisions / Conclusions

- Developer code should not be patched manually into running pods or `pip install -e`'d after the fact; the reproducible path forward is to have the Helm chart's entry-point logic perform a configurable `git clone` (repository/branch specified in the values manifest), guarded by a conditional on whether a local Python module is requested. This was agreed by Marco Mascheroni and Valentin Kuznetsov.
- Deployments should always be done via a full `helm uninstall` followed by `helm install` (clean state, including PVC recreation) rather than `helm upgrade --set` on top of an existing installation, since the latter does not reproduce the installation from scratch.
- `pip install -e` (editable install / DiracX's mounted-Python-modules mechanism) will still be used to inject developer code, since DiracX discovers runnable tasks via Python's entry-point/package registry and a plain `PYTHONPATH`-based approach caused exceptions; Valentin's disagreement with using `pip install` inside the pod at all was noted as not currently critical, since the more urgent problem is reproducibility of the Helm install itself.
- For now, the team will continue using whichever S3-compatible object store is already deployed in each environment (seaweedfs for local/"pixel" runs, MinIO on the CMS web Kubernetes cluster) rather than investing in switching to CERN's S3 service or resolving the licensing question immediately.
- For proof-of-concept purposes, credential handling for the Kubernetes-submitted Monte Carlo test job can follow whatever CRAB currently does, or even just add the X509 proxy as a plain input file, rather than solving this properly now.

## Discussion

- DiracX supports two types of "mounted Python modules" for developer code, one being an "editable" module; Marco's current approach is a `git clone` into the pod's `SRC` area followed by `pip install -e .`, relying on Python's package registry so DiracX can discover installed tasks (e.g., the Condor-submission-monitoring task from the proof of concept).
- The CMS web Kubernetes cluster (via Usacorn) uses a storage class configured to delete PVCs on `helm uninstall` and return them to the pool, due to a PVC quota constraint; this makes any state manually created inside a pod (such as a `git clone`d repo) non-reproducible across reinstalls.
- Valentin Kuznetsov's general design view: Kubernetes should host stable, tested images for integration testing; developers should test locally in their own environment however they like, but only promote tested, stable images to the cluster. He noted the DIRAC team appears to take a different, shorter-term view of bringing developer code directly into Kubernetes for rapid iteration, and said he hasn't discussed with them whether this is meant to be long-term.
- A LHCb-hosted CVMFS instance provides a DIRAC client usable by anyone; setup instructions have been posted to the team's Mattermost channel. Once test18 is confirmed working, users need only a small authorization configuration-file addition and standard CERN SSO to submit jobs.
- Current proof-of-concept job flow: direct job submission → DIRAC job database → a Marco-implemented server-side task polls the database, submits matching jobs to HTCondor, and marks them "submitted." Missing: a task that checks job completion status and updates the database accordingly.
- S3/object storage: DiracX's local setup uses seaweedfs (a Go-based S3-protocol library); the CMS web cluster instead uses MinIO. Valentin was not convinced by seaweedfs's licensing terms, which he linked to budgeting concerns, and noted there is no CMS-collaboration-level commitment yet to adopt S3 broadly. CRAB already uses CERN's existing S3-compatible object store to ship user code sandboxes to worker nodes; Marco hopes that CMS's DiracX S3 usage could similarly point at CERN's existing service via URL configuration, but this is unconfirmed.
- Kevin Lannon noted that CMS previously considered (and did not pursue) unifying WMAgent (production) and CRAB (analysis) tooling, partly because production historically didn't need to handle per-user sandboxes the way analysis does; he argued sandbox handling should be treated as a central, first-class concern in the DIRAC-based architecture rather than an edge case, and noted DiracX's S3-based sandbox mechanism seems to already reflect that.
- Valentin noted DiracX itself appears to depend on more than one S3-related library (MinIO and another one he referred to as "CVEED") for reasons that are unclear to him, adding to his uncertainty about the actual internal S3 requirements.
- Camille Mauceri's exploratory work (with Marco, screen-shared, consulting ChatGPT): attempting to get the DIRAC client to upload files listed under an `InputSandbox` JDL attribute to the server's S3-backed sandbox store; not resolved by the end of the meeting. Camille noted needing to tar multiple files before upload and that the client's upload path appears to involve HTTPX.
- Camille had been including her X509 proxy in the input sandbox as a way to authenticate a Monte Carlo test job's access to the Kubernetes cluster, and questioned whether this was secure; Marco noted CRAB uses a CMS-provided tool for credential movement and suggested this, or simply treating the proxy as a plain input file, would be acceptable for the proof-of-concept stage.
- Marco mentioned the DIRAC team is reportedly planning to replace Boto (the library currently used for S3 access in the DIRAC client) with something else, per a prior DIRAC development meeting, meaning current client behavior around S3 access may change.
