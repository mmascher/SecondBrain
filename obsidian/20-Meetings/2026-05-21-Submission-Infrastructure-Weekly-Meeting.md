# Submission Infrastructure Weekly Meeting

## Summary

Antonio opened with news that Pat is ending their term as the CMS Level-1 lead and will be succeeded by Daniel Espiga starting in September; Antonio noted Espiga is already involved in resource allocation, acquisition, and matchmaking topics and is familiar with the Submission Infrastructure team, which Antonio considered a positive for the team.

Luis then presented a postmortem on a weekend front-end incident: new pilot starts were completely interrupted from Saturday night until Monday around 1–2 PM. The root cause was that Puppet had been disabled on the global front-end machine for more than 30 days; one of CERN IT's automations removed the machine from a LanDB set because Puppet was disabled, and that LanDB set was responsible for a firewall rule allowing pilot traffic to the front-end web server from outside the CERN network. With that rule gone, pilots could no longer download their configuration/validation files at startup, causing widespread pilot-validation failures (particularly visible at Tier-2s, which have higher pilot turnover than Tier-1s). The fix was re-enabling Puppet and waiting for the firewall rule to be reapplied.

Discussion covered why Puppet had been disabled (to test configuration changes without Puppet overwriting them) and the failure to re-enable it afterward and puppetize the changes permanently — Antonio speculated this was connected to the end of Florian's term and to the team being heavily focused on CHEP-related deliverables in the preceding weeks, which meant relevant alert emails were not carefully reviewed. The group discussed several possible mitigations (see Decisions/Action Items) including alert cleanup, a critical-vs-warning alert distinction, a possible fallback mechanism for pilots to fetch configuration from the secondary/backup front end (flagged as needing feasibility verification), and a reminder/checklist for operator handovers. Antonio noted the incident's practical impact was limited because the HTCondor pool has significant inertia (no central-manager crash, and the pool recovers quickly — resources ramp back up much faster than the earlier gradual deflation — once pilots can start again).

There was also a discussion, prompted by Antonio, about where postmortems and related action items should be tracked going forward — the team's documentation site (mkdocs-based, deployed at CERN, requiring CERN login) versus Jira versus the existing weekly-notes/action-item workflow. No firm decision was reached; see Discussion section below.

Hyunwoo raised two additional items. First, he has been unable to log into lxplus.cern.ch (password prompts repeat without reaching two-factor authentication) despite his CERN/CMS account status otherwise appearing fine when checked via the CERN account-management pages; the group suggested checking for an outdated alias/hostname and confirmed the correct current address is lxplus.cern.ch, and Marco pointed Hyunwoo to relevant private messages (resource portal check, and a link to sign the Acceptable User Policy). Hyunwoo was advised to open a ServiceNow ticket with CERN IT if the issue persists.

Second, Hyunwoo raised a question originating from Dave Mason in a Fermilab group meeting: given frequent Linux/kernel vulnerabilities requiring urgent patching and reboots, what should the team do if a future critical vulnerability has no available mitigation? Hyunwoo is drafting a technical plan: at the global negotiator level, disable matching between CMS CRAB schedulers and CMS Connect specifically for jobs directed to the Fermilab Tier-1 (T1_US_FNAL) or Tier-3 (T3_US_FNALLPC), since production jobs do not originate from CRAB/CMS Connect and only user jobs would be affected. This would require negotiator configuration changes (potentially via stopping the negotiator on the primary collector, VOCMS0141, to fail over to the backup collector where he can apply new configuration) and access that depends on Hyunwoo first recovering his lxplus access. Marco noted this would need to be paired with communicating to users (e.g., via CRAB) that jobs targeting Fermilab-only datasets are temporarily blocked, and that placing the site in the "waiting room"/"morgue" state alone would not be sufficient since production jobs should still be allowed. Hyunwoo said this is not urgent and intends to raise it again in two weeks when Antonio is present.

Luis then raised a related, more structural idea: the underlying reason such vulnerabilities are a threat is the relatively weak isolation between the worker node and the payload's container environment (i.e., a malicious payload could potentially escape a container and reach the worker node). He suggested microVMs — a virtualization technology used in public clouds (e.g., AWS Lambda) that offers VM-level isolation (separate kernel) with near-container startup speed — as a possible multi-year direction to explore. Whether pilots (running as unprivileged users) could start microVMs themselves, or whether this requires site-admin/root-level enablement, is unknown and flagged as needing investigation; if the latter, Marco suggested this would likely need to be raised at the WLCG level (rather than as a CMS-only campaign) since all VOs sharing this concern would benefit. Marco said he would raise awareness of this in WLCG forums, and Luis agreed to research microVMs further.

Marco gave an update on testing Stefano's HTCondor concurrency-limit mechanism: because only one replica of the mini-AOD dataset currently exists due to storage-space limitations, jobs are effectively constrained to whichever site holds that replica (giving users only a fraction — e.g., ~10%, cited alongside another site's ~50% — of that Tier-1's capacity for such datasets). Stefano's approach expands a job's eligible site list (e.g., adding well-connected US Tier-2s as remote-read targets for T1_US_FNAL) so jobs can run elsewhere and read data remotely, but this raises the risk of saturating the network or overloading the storage element if too many jobs run concurrently. HTCondor concurrency limits are used to cap the number of jobs of a given type — implemented via a job ClassAd attribute (e.g., "T1_US_FNAL_CRAB_overflow") added by CRAB when a job normally reading data at Fermilab is migrated to run at another site, with a negotiator-side concurrency-limit configuration capping that class to 20 concurrent jobs in the current ITB test. The feature has been working in ITB; the team wants to wait until Stefano (currently on vacation, not attending CHEP) is back before enabling it in production.

Luis gave a factory-operations update: a generally quiet week for tickets with steady progress on existing items. He highlighted a change to increase the KIT GPU entries' memory limit from 20 GiB to 22 GiB (requested due to production jobs failing under the previous limit), announced on CMS Talk; the same change still needs to be made at Fermilab, which Hyunwoo acknowledged and committed to following up on. Luis also reported progress on the HTCondor-CE entries' migration from grid-proxy to site-token authentication: a draft PR with the changes is open and being tested in ITB; of 200+ entries tested, 30 currently fail, of which about 27 are expected/inactive (manual pilots, test entries, etc.) and 2–3 appear to be genuine unreachable-CE problems still to be investigated (Marco suggested also cross-checking those with an X.509 proxy to isolate whether the failure is token-specific or a general CE issue). Hyunwoo asked Luis to document this CE-testing approach on the team's documentation site for reuse; Luis agreed to write it up, alongside a page on the entry-vs-site-token change.

The meeting closed with brief personal/organizational notes: Marco mentioned he had been at Fermilab the previous week (missing Hyunwoo, who was on vacation) as part of a cross-experiment visit that he thought could become a yearly event; and Marco relayed to Luis that he had spoken with Dave Dykstra (Luis's Frontier Squid supervisor) to flag that Luis has been spending more time on Submission Infrastructure work, with an understanding that Luis would shift back toward more Frontier-operations work after CHEP once things quiet down on the SI side. The next weekly meeting will be skipped due to CHEP, resuming in two weeks; Antonio and Florian are attending CHEP in Thailand.

## Decisions / Conclusions

- The team will wait for expiration/normal review cycles rather than take further action on most of the individual factory alert types discussed; the priority is to clean up and reduce alert noise so real signals are not missed, rather than to add new alerting mechanisms.
- Alerts should be split into (at least) two categories: non-critical items visible on a dashboard for proactive review, and critical items that trigger an email — with "critical" clearly indicated in the subject/title — so that recipients know which alerts must be acted on immediately.
- The team currently already has a dedicated alert for Puppet not having run on a host, and a separate alert for the HTCondor pool size dropping below a threshold (originally built by "Zakib" a few years ago); both were confirmed to exist, though the pool-size alert's threshold may not have been triggered during this incident and may need review.
- No decision was reached on replacing or supplementing the current notes-based action-item tracking with Jira or the documentation site for postmortems; the team will continue using Jira mainly for individual/optional task tracking (Luis was encouraged to try it) rather than as the primary postmortem/action-item venue, at least for now.
- The impact of the front-end incident is understood to have been limited because of the HTCondor pool's inertia (no central-manager crash) and its ability to ramp back up quickly (steep recovery slope) once pilots could start again.

## Discussion

### Front-end incident postmortem
Luis walked through the postmortem: Puppet had been disabled on the global front-end machine for over 30 days (originally to allow testing configuration changes without Puppet overwriting them), and CERN IT's automation removed the machine from a LanDB set specifically because Puppet was disabled. That LanDB set provided the firewall rule allowing external pilot traffic to reach the front-end web server, so once removed, pilots could no longer download their startup configuration/validation files, causing pilot-validation failures — more visible at Tier-2s due to their shorter pilot lifetimes and higher turnover than Tier-1s (where 16-core pilot lifetimes had previously been deliberately increased to reduce the relative impact of pilot draining on scheduling efficiency). The fix was simply re-enabling Puppet and waiting for the firewall rule to be reapplied. Antonio described the likely root cause as insufficient diligence in moving successfully-tested changes into permanent (puppetized) configuration and re-enabling Puppet afterward, speculating this was connected to the end of Florian's operator term and to the team's focus on CHEP-related deliverables in preceding weeks, during which relevant alert emails (including a Puppet-not-running notification) went unnoticed amid a high volume of other emails.

### Alert handling and noise
Multiple alerts related to this incident already existed (Puppet-not-running, sent to CMS glideinWMS admins; a separate HTCondor-admins list receives different alerts such as ITB dev front-end proxy creation errors) but were not acted on because recipients had accumulated too many alerts and had started filtering/ignoring them, including via email folder rules. The group agreed the priority is to clean up and reduce alert volume so that remaining alerts are meaningful, and to add a clear critical-vs-warning distinction (e.g., in the email title) so recipients know which alerts require immediate action versus which can be reviewed proactively via a dashboard. Antonio noted the team does not have formal 24/7 on-call coverage, so while a quick weekend response is appreciated, it should not be relied upon — reinforcing the case for better automated safeguards rather than only alerting.

### Documentation venue for postmortems
Antonio raised whether postmortems should be published on the team's documentation website, noting it is a great initiative but questioning whether the site (which requires CERN login and may not be fully public) is the ideal tool given concerns about appropriately balancing internal transparency with not fully exposing operational issues externally. He suggested Jira as a possible alternative, since it is more structured/searchable and commonly used for internal issue tracking, and could allow linking specific tasks to specific incidents. Luis was open to evaluating Jira, noting his current approach (a markdown file) is easy but static and lacks collaboration features; he mentioned prior experience using Google Docs for this purpose at a former employer but was unsure of its fit here. Marco noted the team has historically used Jira only sparingly and tends to rely on the weekly-notes action-item workflow instead, while agreeing Jira could be a good fit specifically for Luis's own task tracking; he offered to share the link to the team's existing CMSSI Jira project and suggested revisiting old Jira issues at some point to close out stale ones.

### Operator handover checklist
As a lower-priority item, Luis suggested creating a checklist of things to verify when an operator's term ends (e.g., confirming Puppet is running, no uncommitted configuration left behind). Antonio agreed this reflects insufficient diligence in this case and recalled that in the past, operators would shift toward writing documentation and stop making changes toward the end of their term — implying this practice may not have been followed this time.

### Hyunwoo's CERN account access issue
Hyunwoo reported being unable to log into lxplus.cern.ch (repeated primary-password prompts without reaching two-factor authentication), despite his general CMS/CERN account status appearing fine via the CERN account-management pages (including the relevant computing group association). Antonio suggested checking for an outdated alias/older hostname pointing to a legacy version of lxplus; the current correct address (lxplus.cern.ch) was confirmed by Hyunwoo to still fail. Marco pointed to private messages sent earlier covering the CERN resource portal (to check central computing service status) and a link to (re-)sign the Acceptable User Policy (AUP), noting these can lapse and require periodic re-acceptance. The group advised opening a ServiceNow ticket, which routes to CERN IT, as the way to formally report the issue if it persists.

### Contingency plan for unmitigatable vulnerabilities
Hyunwoo relayed a question from Dave Mason (raised in a Fermilab group meeting) about what the team would do if a future critical Linux/kernel vulnerability had no available patch/mitigation, given the increasing frequency of such vulnerabilities. Hyunwoo's draft technical approach is to disable HTCondor negotiator matching between CMS CRAB schedulers/CMS Connect and the Fermilab Tier-1/Tier-3 (T1_US_FNAL / T3_US_FNALLPC), since production jobs do not come from CRAB or CMS Connect, meaning only user jobs would be blocked. This would require negotiator configuration changes; Hyunwoo described a possible approach of stopping the negotiator on the primary collector (VOCMS0141) so the negotiator moves to the Fermilab backup collector, where the new matching rule could then be applied — but this depends on Hyunwoo regaining lxplus access and receiving appropriate primary-collector access from Marco/Antonio. Marco agreed this was a reasonable approach but noted it would need to be paired with informing users (e.g., via CRAB messaging) that jobs targeting Fermilab-exclusive datasets are temporarily unavailable, since placing the site in the "waiting room"/"morgue" state alone would still allow (and be intended to allow) production jobs to continue. Hyunwoo said he is not aware of other sites/experiments considering a similar plan and believes Fermilab may be first to think about this; he plans to raise the topic again in two weeks when Antonio is present, noting it is not urgent but rather preparatory.

### MicroVM isolation idea
Luis connected the vulnerability-contingency discussion to a broader structural point: such Linux/kernel vulnerabilities are primarily a threat because containers share the host kernel with limited isolation from the worker node. He introduced microVMs as a virtualization approach (used in public-cloud function-as-a-service platforms, e.g., AWS Lambda) offering VM-level isolation (separate kernel, hardware virtualization) with near-container startup times (milliseconds), positioning it as a potential multi-year direction to reduce or eliminate this class of risk. Whether an unprivileged pilot could launch a microVM itself, or whether this requires elevated/site-admin-level enablement, is unknown. Marco noted that if site-admin action is required, this would be a matter for the whole WLCG (since all VOs would benefit), rather than something achievable via a CMS-only site campaign, and said he would raise it in a WLCG forum to build awareness; Luis agreed to research the technology further. Hyunwoo commented more broadly that AI-driven security threats are moving faster than human response capacity and that this class of technical mitigation should be part of a larger ongoing discussion.

### CRAB overflow concurrency limits
Marco described ongoing work (led by Stefano) using HTCondor concurrency limits to safely expand the set of sites eligible to run jobs needing data currently available only as a single mini-AOD replica (due to storage constraints), which otherwise heavily constrains available capacity at the hosting Tier-1 (cited examples: roughly 10% vs. 50% of a Tier-1's resources being available for such datasets). The mechanism adds a ClassAd attribute (e.g., "T1_US_FNAL_CRAB_overflow") to jobs that CRAB migrates to remote-read data from another site, and a negotiator-side concurrency limit caps the number of concurrently running jobs carrying that tag (currently 20 in ITB testing) to avoid saturating the network or overloading the storage element. This has been working in ITB; production enablement is planned but deliberately deferred until Stefano returns from vacation (he is not attending CHEP). Luis clarified this is distinct from an overflow mechanism Stefano had separately presented at a facilities meeting.

The equivalent change still needs to be applied at Fermilab; Hyunwoo acknowledged Luis's private message about this and committed to making the change.

Of 200+ entries, 30 currently fail; ~27 of those are expected (manual pilots, test/inactive entries), leaving 2–3 genuine unreachable-CE cases still to investigate, with Marco suggesting a cross-check using an X.509 proxy to distinguish a token-specific problem from a general CE problem. Hyunwoo asked Luis to document the testing methodology and the entry-vs-site-token change on the team's documentation site.
