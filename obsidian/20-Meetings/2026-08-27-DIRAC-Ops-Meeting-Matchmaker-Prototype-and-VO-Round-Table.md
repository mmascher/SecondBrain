## Decisions / Conclusions

- No specific decision was reached on whether to backport the "disk 6" race-condition fix; it was agreed the race condition is difficult to reproduce reliably and not urgent enough to justify building a dedicated integration test at this time, but Xiaomei Zhang will attempt to trigger it opportunistically in a near-production environment.
- In the Helm chart, SeaweedFS is now the S3-compatible service used for local/development deployments; MinIO is being phased out of the chart because it is described as "basically dead as a product" and no longer provides binaries. Production users are not required to use either — any S3-protocol-compliant provider is supported, and if SeaweedFS is used in production it should be maintained separately from the chart, following SeaweedFS's own documentation.
- There is currently no effort to build a DIRAC/DiracX-native S3 storage element (i.e., no plan to implement a DIRAC-managed S3 storage backend using the DIPS protocol); S3 is used purely as a generic external storage backend accessed like any other S3 storage.
- The DIRAC sandbox-store service now acts as a proxy in front of S3-compatible storage (rather than storing sandboxes on local disk), which means it can be, and currently is, horizontally replicated (2–3 instances reported running in OKD).
- The Helm chart's inclusion of a specific technology (e.g., SeaweedFS for S3, or a bundled MySQL) does not obligate operators to use it — the chart implements against standard protocols (S3, MySQL), and operators may substitute their own compatible service, taking on responsibility for operational concerns (patching, upgrades) themselves.

### S3 object storage rationale
A discussion (prompted by a question referencing S3 licensing considerations, possibly at CERN's storage service) covered why DIRAC/DiracX uses S3-compatible object storage:
- Job sandboxes (files that may be shared/reused across many jobs — scripts, small input files, etc., but explicitly not large physics data such as AOD/"dst"-scale files) used to be stored on the local disk of a single machine, which does not scale (limited I/O, single point of failure) as deployments grow.
- Grid storage elements are a poor fit for this use case: they are not designed for a single small file being accessed by thousands of clients simultaneously and become overloaded under that pattern, whereas S3-compatible storage handles this well due to its caching layers. One deployment was cited with roughly 2 TB of data spread across around 65 million objects, illustrating typically small average object size.
- The chart does not require a specific S3 provider — any provider implementing the required subset of the S3 protocol (e.g., checksum-verification headers) works. SeaweedFS is bundled in the chart as a convenient option for local/development use, not intended for production use as-is; MinIO, previously used similarly, is being phased out as it no longer provides binaries and is considered a "dead" product.
- Marco Mascheroni noted the `test18` DiracX Kubernetes deployment currently still uses MinIO rather than SeaweedFS, which will need to change at some point. He also noted CRAB uses S3/S3-like storage at CERN for a similar purpose (sandboxes/user code for grid jobs).
- Andrei Tsaregorodtsev clarified a separate question: whether there is a DIRAC-native S3 storage element (implementing DIRAC's own storage-element interface/DIPS protocol) — the answer was no such effort exists; S3 storage used by DIRAC/DiracX is treated as an ordinary external storage backend, not something DIRAC customizes or manages itself. He also noted a niche historical use case of the legacy DIRAC storage-element abstraction: quickly exposing a local filesystem as a DIRAC storage element without extra installation, which is not available for S3-based setups without installing an S3-compatible service; he agreed to forward more detail on this use case.
- It was also clarified more generally that using a given technology (S3 provider, or MySQL) within the Helm chart does not bind production deployments to that same technology, as long as the chart's required protocol is honored; operators substituting their own service take on the associated operational responsibilities themselves.

### Redis-based matchmaker/scheduler prototype (internship presentation)
An intern referred to as "Jan" (surname not given in the transcript), introduced by a colleague (name transcribed inconsistently as "Alexandra"/"Alexander"), presented the outcome of a roughly five-month internship: a prototype of a potential next-generation matchmaking/scheduling system intended to eventually replace the legacy DIRAC matchmaker, which was described as valuable but not well suited to a shifting grid-computing landscape (more complex resource/image constraints, e.g. from AI-related workloads). The stated design goal was to sustain up to 1,000 matching requests per second against up to 10 million waiting jobs.

**Matching flow presented:**
1. A pilot requests a job, advertising hardware characteristics (OS, CPU, GPU, etc.).
2. Jobs are filtered to those technically compatible with the pilot's advertised characteristics; if no compatible job exists, matching ends with no result for this pilot.
3. A "quota"/running-limit stage applies per-job-type running limits (equivalent to legacy DIRAC's running-limit mechanism, e.g. used to avoid overloading a site with too many fast Monte Carlo jobs) together with share-based splits between job classes (e.g., an example split of 80% production / 20% user jobs was given as illustrative, not necessarily final).
4. The remaining eligible candidates are ranked by a fair-share mechanism (by group, then owner), with ties broken by FIFO submission time.
5. The top-ranked candidate is selected, its status updated, and the job returned to the pilot.

**Technical approach:** requirements were formalized using data models built with Pydantic (referred to in the transcript as "Binom tik"). Prototyping proceeded incrementally to isolate bottlenecks: (1) a pure-Python + SQLite baseline to validate the matching logic; (2) a Python + Redis hybrid; (3) matching logic pushed fully server-side into Redis via Lua scripting, executed as an atomic operation (avoiding per-command network round-trips). Performance testing used Locust to simulate up to around 10,000 simultaneous pilots. The pure-Python/SQL baseline achieved only around 33 matches/second, far below the 1,000/s target. Moving to the Redis-hybrid approach surfaced network and JSON-serialization bottlenecks, leading to the conclusion that matching logic needed to run "closer to the data" — i.e., inside Redis itself. This led to a sharded ("children") architecture where jobs are partitioned into requirement-specific buckets at submission time (e.g., "pending GPU," "pending LCG"), so a pilot's request only searches compatible buckets, giving fast reads. An actively-worked-on open issue is the combinatorial explosion of complex requirement combinations and the logic needed to manage it. The prototype intentionally uses only core Redis features (not additional Redis modules) to avoid extra internal blocking risk. No benchmark result against the 1,000/s-for-10M-jobs target has yet been achieved; work on the Redis-based solution is ongoing.

**Discussion / Q&A:**
- Daniela Bauer asked (1) whether this creates new infrastructure/deployment requirements, given DIRAC/DiracX doesn't usually operate at this scale — answer: Redis is already used elsewhere in DiracX (e.g., for the DiracX task queue/DiracX tests), so no new requirement is expected; and (2) whether multi-VO usage (since there is currently a single matcher across all VOs) could cause unexpected side effects — answer: VO is simply one of the matching criteria a pilot advertises, like any other requirement, so multi-VO matching is expected to work naturally as long as pilots remain single-VO (no interest was expressed in supporting multi-VO pilots).
- Andrei Tsaregorodtsev asked how duplicate matching of the same job by multiple pilots is avoided. Answer: Redis's sequential internal execution model (via the atomic Lua script) avoids the need for explicit locks, since there are no network round-trips within the matching logic itself; sequential per-request processing was said to remain fast enough (sub-second) to sustain the target load. Andrei confirmed his understanding that this effectively replaces a single large SQL query with an equivalent (but sequentially executed) operation.
- Andrei also asked how fair-share accounting information (counts of jobs already assigned per group/owner) is fed back into ranking. Answer: this is updated directly inside Redis at assignment time, without a round trip to a separate central store. It was noted that, unlike legacy DIRAC — where fair share is implemented as a dynamic modification of job priority, and which also involves some randomness that makes it hard to reproduce for integration testing — the new prototype treats priority/quota and fair-share ranking as separate, and intends the fair-share ranking itself to be deterministic (FIFO within tiers).
- I Ueda asked for clarification of "quota" vs. "priority"/"share" terminology: the 80/20-style production/user split was agreed to be more accurately described as a "share" than a strict priority; "quota" refers to the per-job-type running-limit mechanism at a site (as in current DIRAC). I Ueda also asked when the candidate list could end up empty — clarified as corresponding to the current concept of (effectively) empty task queues: if no eligible job type has jobs available, or all eligible job types have hit their running limits, the pilot receives no match.
- Andrei asked whether the concept of task queues still exists in the new design, since the presented diagram shows individual jobs. Answer: the task-queue concept is now represented implicitly by the bucket/key structure of the Redis key-value store (each key roughly corresponds to a former task queue, holding the jobs assigned to it); however, the current proof-of-concept still effectively treats every individual job as its own task queue rather than grouping jobs into shared buckets, which Andrei suggested could be "overkill" given up to 10 million jobs would then participate directly in matching. In response, it was argued that the 1,000-matches/second requirement is the more binding constraint than the raw number of waiting jobs, and that Redis's in-memory job/count state can be treated as non-critical/rebuildable from the job database (source of truth) if Redis needs to restart — though efficiently refilling Redis after a restart was noted as itself a requirement. Sizing the expected number of task queues was described as hard, since task queues are expected to be very asymmetric in how full they are (a small number likely containing most jobs).
- A participant (room label) raised two points framed as suggestions/opinions, drawing on CMS experience, not decisions: (1) tying quotas to raw job counts could create accounting problems once jobs have heterogeneous resource requirements (e.g., single-core vs. many-core jobs); suggested considering quotas defined by resource usage (e.g., modeled I/O or network usage) instead — not decided, but noted DIRAC already partitions similar jobs into different job-type buckets as an approximation of this; (2) the presented flow appears to lack a final handshake between assigning a job to a pilot in the data store and the pilot's worker node actually receiving/executing the job payload; warned that adding such a handshake inside the Redis-based matching path itself would likely hurt performance (implying a round trip to the pilot), and suggested job reservation/recovery (handling lost handoffs, returning jobs to the queue) should be treated as a separate concern from matching, similar to mechanisms believed to already exist in legacy DIRAC/WMS for this.
- Marco Mascheroni asked whether there is also an earlier matchmaking stage deciding whether to send a pilot to a worker node at all (as in glideinWMS's two-stage matchmaking — first deciding whether to send a pilot, then matching jobs to pilots), e.g. avoiding sending a GPU-capable pilot to a resource when no GPU jobs are queued. Answer: this exists in current DIRAC (pre-pilot-submission checks); it can be partly redundant for installations that saturate most resources anyway, but needs to remain available as an option, particularly for smaller installations with bursty submission patterns where continuous pilot submission would be wasteful.
- Andrei reiterated that, given a stated goal of 10 million waiting jobs, some formal notion of task queues still seems necessary so that matching doesn't need to scale with the number of individual jobs; this was broadly agreed, with the 1,000 Hz matching-rate requirement identified as the primary driver, and the number of waiting jobs treated as more flexible/rebuildable state.
- The chair raised a broader, more managerial question about next steps, noting that Jan (the intern) is leaving soon and asking how the resulting code and knowledge should be carried forward. The response (not a decision) was that the internship's original goals have not been fully met, this is not currently the highest-priority project, but its priority may need to rise given the risk of accumulated knowledge fading once Jan leaves; next steps include seeing how far the internship work can get before it ends, then determining how to integrate or continue it (potentially with another student or other volunteers), including resolving open questions such as behavior on service restart/shutdown. No concrete continuation plan or owner was assigned.

### DIRAC production/transformation system requirements form — response summary
A Google Form requesting requirements for the DIRAC production/transformation system, circulated previously, had received 6 responses by this meeting, including from communities referred to as CMS and "Ruben" (the latter noted as likely outside the core DIRAC community); some communities (referred to as "CTA-led," "FC") had not yet responded, and a reminder had reportedly been sent the previous day. - Everyone uses CVMFS for software distribution.
- Operational models are broadly similar: systems tend to be run/operated by a small number (one to a few) of core experts.
- Usage models are broadly either "analysis" or "production" style, similar to what has mostly been presented in this meeting/community so far.
- Pain points are similar across communities: debugging transformation-system-specific issues is regarded as hard by everyone.
- The current transformation system does not provide certain workflow-level capabilities that were mentioned but not fully captured in the transcript.
- Transformation-system-specific analytics/accounting have been requested; this is not directly available today, though DIRAC's WMS-level accounting could serve as a layer to build on.
- There is no proper workflow validation in the core system; this is sometimes implemented in extensions rather than centrally.
- Every community has a different metadata system, without a clearly defined common interface between them.
- Nearly every respondent mentioned they would welcome an AI assistant, not limited to debugging use cases.
The chair noted these summary points, and the full (public) responses, would feed into the forthcoming ADR, which is still being finalized pending some details — a rough estimate of "end of next week" was floated for the ADR, contingent on a colleague referred to as "Kristoff"/"Christophe" returning from being away.
