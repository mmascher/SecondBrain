## Decisions / Conclusions

- The group agreed to wait for the official kernel patch backport to AlmaLinux (expected within roughly 24 hours) for the "copy fail" vulnerability, rather than apply an interim fix, since central managers and other machines would need a reboot regardless when the permanent fix lands, and this avoids rebooting twice.
- Local/VO-box machines and Submission Infrastructure machines were assessed as low risk for the "copy fail" vulnerability because they are not openly exposed to SSH from outside (requiring CERN e-group membership, VPN, and — for most Submission Infrastructure machines except SCEDDs — two-factor authentication); Luis noted the vulnerability still requires a prior step of gaining unprivileged remote execution on a machine before it can be exploited to escalate to root.
- For GPUs partitioned via NVIDIA MIG, HTCondor discovers each MIG instance as an independent GPU (similar to a full GPU from HTCondor's perspective); the control developers recommended against `-divide`-style manual partitioning of GPUs due to job isolation/resource-clash risk (a risk already present, to some extent, with memory overloading on CPU jobs).
- MIG-based GPU memory partitioning is static per instance; if a job requires more memory than a given partition provides, it cannot be matched to use the full device's memory, effectively rendering that capacity unusable for such jobs — analogous to how CPU/memory can already be constrained by site-admin configuration (e.g., hyper-threading) independent of the physical hardware.
- The Condor-C-to-site-token migration Luis is working on is an internal authentication detail between the factory and the CE (per entry), not a broader change to CMS's token migration status; CMS pilots already carry both grid-proxy and token credentials and are not currently restricted to tokens only, so removing the grid-proxy fallback needs to be done carefully to avoid breaking sites that may be silently relying on it.
- The CPU-time and missing-CPU-count reporting issues for Condor-C sites are understood to have two separate causes: an old HTCondor version at Caltech's Condor-C batch system (last updated in 2022, version ~10, versus current versions 23-26) likely explains the missing CPU-count reporting for some CEs; the ARC-CE (seconds) vs. Condor-C (minutes) factor-of-10 discrepancy in reported CPU time is suspected to be a separate bug, possibly already addressed by a newer factory-side HTCondor version, but this is unconfirmed and both are considered minor/corner-case issues for now.
- The new aggregated (all-Tier-1 / all-Tier-2) pilot-efficiency dashboard, built by removing the per-site filter and instead matching on site strings starting with "Tier 1"/"Tier 2" and computing total-wall-time / total-CPU-time ratios (rather than averaging per-site efficiencies), shows meaningfully reduced fluctuation and a more than 10% apparent efficiency increase for Tier-1s compared to the earlier per-site view; Tier-2s show a similar but smaller effect, and are believed to be further improvable by separating overloaded from non-overloaded Tier-2 sites.

### GPU MIG partitioning, matchmaking, and the "VO card" concept
The key takeaway on GPUs was that once a site admin enables NVIDIA MIG, HTCondor discovers each MIG instance as an independent GPU device, much like a regular GPU. The control developer recommended against a `-divide`-style manual partitioning approach (declaring the same device multiple times) because jobs could clash or use more memory than declared — a risk Marco noted already exists to some degree with regular memory overloading on CPU jobs, though possibly more delicate with GPUs given their relative novelty. Antonio confirmed this technically differs from MIG's proper instance isolation.

A question was raised about whether a single job could use multiple MIG instances simultaneously; TJ (per Marco, relaying the control developers' input) indicated it cannot. This raised a further question about static memory partitioning: since MIG instances have a fixed share of GPU memory, a job needing more memory than one instance provides cannot be matched, even if the physical device has enough free memory overall — Luis confirmed this understanding (mentioning HTCondor's suggested fix being to update to the latest HTCondor version) and noted neither the control developers nor NVIDIA sales support representatives they'd spoken with were familiar with MPS (Multi-Process Service) as an alternative approach; this remains unexplored/untested.

Antonio connected this to the existing "VO card" concept (used for CPU resource pledging), which defines the minimum usable "slot" in multiple dimensions (e.g., a CPU core must come with at least 2GB memory, be available 48 hours, have a minimum amount of disk, etc.) — conditions that can be imposed by the VO on sites when resources are formally pledged to the experiment (as opposed to opportunistic resources, where CMS has no such leverage and simply uses what fits). Antonio noted CMS currently has no equivalent standard/typical-job definition for GPU resources, describing this as a "chicken and egg" problem: GPU resources can't be properly tested without representative jobs, and representative GPU jobs can't be defined/benchmarked without sufficient GPU resources to test against. He tied this to the ongoing GPU benchmark-definition effort, which is intended to eventually allow testing whether a given GPU resource configuration is usable for CMS's needs.

Separately, Luis raised (referencing an earlier discussion with Marco) that the number of MIG slices is currently defined solely by the site admin, and suggested exploring what an optimal number of slices would be relative to a pilot's other dimensions (CPU, memory) — e.g., a 16-CPU pilot paired with an 8-slice GPU would ideally only schedule jobs requesting 2 CPUs and 1 GPU each; two 8-CPU jobs would leave 6 of 8 GPU slices unused. Antonio agreed this is conceptually the same VO-card sizing problem.

### Memory/CPU metric extraction from pilot logs
Following up on the event-logs discussion, Luis confirmed the memory-usage metric of interest is the overall peak memory for a pilot (not a sum of peaks), matching what's needed to compute a memory-utilization/saturation-efficiency metric alongside memory-allocated. Luis noted he still needs to check whether these values are reported consistently across all entries, since (as already known for CPU metrics) some older HTCondor versions at certain sites don't report them.

On the CPU-time discrepancy: Marco explained the factory's Condor-C/ARC-CE mechanism reads batch-system (e.g., Slurm, PBS) memory/CPU usage and CPU time and reports it back as an attribute HTCondor can read; a known issue is that CPU time appears off by roughly a factor of 10 for some sites, possibly because ARC-CE reports in seconds while Condor-C reports in minutes (suspected HTCondor bug). Separately, some sites are missing CPU-count reporting; Marco identified this as likely due to Caltech's Condor-C batch system running an old HTCondor version (~10, released 2022) versus the current 23-26 range, and clarified with Luis that these are two separate, likely unrelated causes — both considered corner cases for now, to be revisited.

### "Copy fail" kernel vulnerability
Antonio noted many sites (including PIC and BSC) are actively working on this vulnerability, sharing information on fixes, testing, and mitigation. He described a local Antonio-managed VO box at PIC (used for Rucio transfers) as low-risk since it is not openly SSH-accessible (VPN/firewall-protected, effectively single-user), and reasoned similarly for Submission Infrastructure machines: access requires first reaching the CERN network (e.g., via LXPLUS, which is assumed already patched) and then CERN e-group membership with two-factor authentication — except that SCEDDs (unlike other Submission Infrastructure machines) do not require two-factor authentication, a detail Marco said he was not previously aware of. Antonio assessed the impact as minimal given these layers of protection, though he noted he lacks the security expertise to make a final call and deferred to whoever needs to apply the changes.

Luis explained the vulnerability turns any local unprivileged user with access to an SUID binary into a root shell, meaning unprivileged remote access could be escalated to root remote access — but this depends on a prior step of gaining that unprivileged execution access in the first place, so it is not an immediately exploitable remote vulnerability on its own. Luis reported the patch is already in the mainline kernel but not yet backported to the AlmaLinux versions in use; after discussing with Dave (Frontier), the decision was to wait roughly 24 hours to see if the backport lands, since applying the kernel update to fix the vulnerability will require a reboot regardless, and doing an interim fix first would mean rebooting twice. The group agreed with this approach.

This is related to changes to the Run 3 HLT farm ("the new word farm") used for data-taking, and represents a reduction (not a majority loss) of Tier-0/P5-associated capacity.

### Monitoring: pilot overloading and efficiency dashboards
Antonio and Luis reviewed new Grafana dashboards, building on an initial plot Luis created the previous day (showing overloaded-true/false status per site for Tier-1s) plus additional plots Antonio added:
- A plot of the number of pilots finishing per time slice, added to help interpret fluctuations in the overloading plot (since fluctuation can result from varying numbers of very short pilots finishing in a given window).
- A total-wall-time plot, added for the same cross-checking purpose.
- An aggregated efficiency plot that removes the explicit per-site condition and instead matches on site strings starting with "Tier 1", computing an overall total-wall-time-to-total-CPU-time ratio (not an average of per-site efficiencies). This showed more than a 10% apparent efficiency increase and substantially less variability compared to per-site plots. A similar (smaller) effect was seen for Tier-2s in aggregate; Antonio and Marco noted this could likely be improved further by separating overloaded from non-overloaded Tier-2 sites, since non-overloaded (generally less efficient) sites dilute the aggregate signal, while for Tier-1s essentially all sites are being overloaded to some degree, converging to a similar efficiency value (~66%) across sites.

The team noted the dashboard currently only has about two days of data; Marco confirmed March data exists and can be backfilled/copied to allow longer-period integration to be tested, which both agreed would help smooth out artifacts (e.g., a visible anomaly at one data point, and a data gap where a site had no pilots terminating in a given window). Luis also noted the Grafana time-interval dropdown only exposes one-hour and one-day presets by default, but arbitrary custom values (e.g., 3-5 hours) can be entered for smoother aggregation.

Marco separately described his original preference for how this monitoring could work as a proper time series — generating a periodic (e.g., every 30 minutes) document per active pilot for its duration, rather than one document per pilot only at termination — which would give more granular, accurate data over time. He proposed this as something to keep in mind and revisit later if the current per-termination approach proves too noisy long-term, but not something to implement now (with CHEP season ongoing). Antonio agreed to wait and evaluate once more data is available, questioning what additional value the finer granularity would add given current information is already informative.

### Post-meeting discussion: obtaining pilot metrics before termination
After Antonio left, Luis connected the monitoring design discussion above to Jamie's earlier email about extracting logs via HTCondor's Python bindings, asking whether it's possible to get pilot metrics before a pilot terminates (rather than only afterward). Marco explained his understanding that the CE mechanism (as currently implemented) learns of a completed batch-system job and reads its metadata (e.g., CPU time from Slurm) only once the job has finished, but suggested this should be confirmed with Jamie.

Luis then proposed an alternative: since Submission Infrastructure fully controls the pilot code, a cron-like payload could be injected into the pilot to periodically (e.g., every 15-30 minutes) call back to a service on the factory with live metrics, which would then push the data to OpenSearch; he assessed this as feasible, though nontrivial to test, and not much harder than the current approach of parsing HTCondor logs. Marco agreed this could work but recommended against implementing it as a one-off Submission Infrastructure script; instead, he suggested Luis propose and develop it within the glideinWMS project (e.g., via the GlideinWMS meeting), so that it becomes a feature maintained over time by the glideinWMS developer community rather than a system that could become unmaintained/broken if the original developer moves on or the current operator lacks the expertise to fix it. Luis agreed this was the direction he was already leaning toward.
