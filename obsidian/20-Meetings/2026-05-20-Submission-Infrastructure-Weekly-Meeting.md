### glideinWMS/HTCondor architecture training
This session continued a training slide deck (a prior session had covered Condor-G). Topics covered:
- **Vanilla HTCondor pool**: the schedd (maintains the list of submitted jobs, primarily for recovery, in a local file rather than a formal database), the collector (a global observer that tracks all pool components, including startds), and the negotiator (queries the collector for available resources and the schedd for jobs, matches them, and grants a claim to the schedd so a job can start on a startd). Because execution nodes are typically behind a firewall, the connection is inverted via the Condor Connection Broker (CCB): the startd publishes its claim to the CCB, and the connection is then initiated from the other direction.
- **Glideins**: a glidein is essentially a properly configured startd, started dynamically as a grid job on a worker node rather than existing as a permanently configured execution node. Multiple glideins (including from different experiments) can run on the same physical worker node. Some sites run glideins inside Docker or other containers (e.g., Fermilab, partly to simplify getting a consistent environment and applying updates by changing a container image rather than updating each worker node individually).
- **Three logical glideinWMS components**: factory (site knowledge, glidein submission), front end (user-job knowledge, request/site-selection logic, job and grid monitoring, credential handling), and the glidein/startup process itself (runtime environment discovery and validation).
- **Factory node internals**: the factory node runs its own local Condor installation (a schedd and collector). The factory (a set of Python processes) submits grid-universe jobs via `condor_submit` to this local schedd to create glideins. The front end communicates with the factory through this local collector, which is used for reporting/monitoring rather than matchmaking — inspecting the factory's `condor_status -any` output showed no active negotiator, confirming the collector here acts more like a message broker. The schedd's grid manager (a sub-process of the schedd) spawns an ARC-CE GAHP or Condor-C GAHP to handle submission to the remote compute element. Running `glideinFrontend`/factory "reconfig" pushes updated entry configuration (from the factory's XML config) into this local collector.
- **Front-end matchmaking ("first matchmaking")**: the front end monitors idle jobs (from CRAB/WMAgent users) in the vanilla-pool schedd and queries the central manager for how many jobs each running pilot is handling, then computes how many pilots each entry should request. There is a deliberate slow ramp-up in submission rather than requesting everything at once, though Marco could not articulate a clear underlying reason for this beyond likely being empirically driven. In practice, the team mostly operates under an assumption of unconstrained ("infinite pressure") demand, with requests capped (e.g., around 100) rather than finely computed — except for specific constrained cases, such as GPU jobs (pilots requested only at GPU-providing entries when GPU jobs are queued) and capacity-limited opportunistic/Tier-3 resources, where requests are more carefully managed. Site selection itself (which sites a job may run at) is decided by CRAB/WMAgent based on data-locality principles, not by the front end.
- **Front end/factory topology**: front ends and factories have a many-to-many relationship. The CMS global-pool front end talks to three factories: CERN (VOCMS0806), Fermilab, and the OSG "Tiger" Kubernetes cluster (Wisconsin), which also serves other experiments (e.g., LIGO, DUNE, IceCube). A fourth OSG factory, "Tempest" (Indiana, also Kubernetes-based), exists but the CMS front end does not currently talk to it. The CERN factory currently serves only the CMS front end, though it briefly served other experiments' front ends as a favor during a period when a glideinWMS major-version upgrade dropped proxy support and OSG had not yet updated to the newer scheme; this arrangement was temporary and low-effort for the team, and is no longer in effect. Marco flagged an email from Brian Lin from the previous week as something to discuss later in relation to this topology, without resolving it in this meeting.
- **Front-end failover**: the front end is not a server (it does not receive external requests); it watches the vanilla-pool schedd and submits requests to the factory's collector. A backup front end (configured at Fermilab) remains passive unless it detects that a specific classad (a "Glide Client Global"-type classad containing the sibling/primary front end's configured name) is missing from the collector, at which point it begins submitting itself. This relies on the collector's normal behavior of dropping classads that are not refreshed within a timeout window (as opposed to keeping them indefinitely), which is how a primary front-end failure is detected.
- **Tokens in glidein requests**: inspecting a Glide Client classad (via `condor_status -l`) showed encrypted parameters (visible even when the requested-glideins count is zero, since the token may simply be expired) containing multiple token types: a **site token**, used to authenticate the factory to the compute element, based on a public/private key pair where the factory holds the private key and publishes the public key via the collector — the CE can decode but did not sign this token; an **ID token**, used to authenticate the startd back to the collector, based on a symmetric key shared within a common trust domain (e.g., the schedd/factory machine); and a separate **data token**, used for data read/write authorization at the worker node, which is user-specific and handled at the schedd/user level rather than by the factory or front end directly. Marco was unsure exactly where the site-token key material is stored, believing this is documented on the glideinWMS website.
- **Operator roles**: front ends are geographically/administratively specific, operated by an admin who sets user-facing policy; factories are more generic and not affiliated with a specific group, with grid monitoring and troubleshooting as their main task — explained as the rationale for having two distinct operator roles.
